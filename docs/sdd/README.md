# Logistics_MEM · SDD 文档体系

本目录是 V1 教学平台的设计与实施事实来源。所有影响用户体验、路由、状态模型或教学流程的改动，先在这里说明，再进入代码。

## 目录

```text
docs/sdd/
├── constitution.md                 # 长期稳定的项目宪法
├── specs/                          # 一次改动一个规格包
│   └── （进行中的规格包）
├── context/                        # 可持续积累的项目上下文
│   ├── tech/                       # 技术架构与边界
│   ├── business/                   # 教学业务与用户流程
│   ├── experience/                 # 视觉、交互、内容体验原则
│   ├── patterns/                   # 可复用 UI / 实现模式
│   └── pitfalls/                   # 已知问题与避免事项
├── templates/                      # 新规格包模板
└── archive/                        # 已完成规格的归档入口
```

## 工作流

1. 在 `specs/` 新建编号目录：`NNN-短名称`。
2. 完成 `spec.md`：问题、范围、用户流、验收条件。
3. 完成 `plan.md`：文件级实现计划、风险与验证方式。
4. 完成 `tasks.md`：可执行、可验证、可勾选的任务。
5. 用户确认规格后才修改生产代码；实现时逐项更新任务。
6. 验证通过后，把规格包移入 `archive/`，并将可复用结论写回 `context/`；001 已归档。

## 规则

- V2 展示源码已由规格 002 移除；后续游戏平台如需建设，必须作为独立项目与独立规格处理。
- 文档描述真实的既有行为；不能用虚构指标填充规格。
- “视觉参考”不是“重写信息架构”的授权：先保持路由、状态与教学闭环，再优化视觉层。
- 每个规格包都必须有明确的范围外内容和验收标准。

详细约束见 [constitution.md](constitution.md)。
